# Как готовить и публиковать статьи на Хабре

Эта инструкция относится к статьям из `docs/articles/` и страницам
`/marketing-preview/habr-*/`.

## Главное правило

Сначала определить одну конкретную пользу для читателя, потом писать статью.
Не пытаться одновременно рассказать историю проекта, перечислить технологии и
прорекламировать сервис. После заголовка читатель должен сразу понимать:

- какая проблема разбирается;
- кому она знакома;
- какое решение он сможет применить у себя.

Писать простым языком, короткими абзацами и без философских вступлений. Любое
техническое утверждение о Doday и любую цифру сначала проверять в репозитории.

## Правила Хабра

- Обращаться к читателю на «вы».
- Не упоминать возраст автора и не строить статью на автобиографии.
- Код показывать обычными блоками кода, а не картинками.
- Ссылку на GitHub размещать отдельной строкой.
- Заканчивать словами «Спасибо, что дочитали».
- Честно указывать, что материал и проект готовятся в паре с ИИ-агентом.
- Подпись автора: Ярослав Боев или ник SwairIt — выбрать один вариант и не
  смешивать их внутри одной статьи.
- Не добавлять изображение только для количества. Скриншот должен подтверждать
  конкретный тезис из соседнего абзаца.

## Настройки публикации

Перед публикацией заполнить все перечисленные ниже поля.

### Обязательные поля

- **Тип публикации:** Статья.
- **Язык публикации:** Русский.
- **Целевая аудитория:** выбрать одну наиболее близкую категорию. Для
  технических статей Doday обычно подходит «Разработка и инженерия».
- **Хабы:** от 1 до 5 существующих хабов. Брать только те, которым посвящена
  заметная часть текста. Название технологии нельзя указывать как хаб, если её
  нет в списке Хабра.
- **Ключевые слова:** от 1 до 10 терминов через запятую. Здесь можно указывать
  фреймворки и узкие технологии, которых нет среди хабов.
- **Текст кнопки «Читать далее»:** до 30 символов, связан с результатом статьи.

### Остальные поля

- **Формат:** «Кейс», если описан реальный опыт Doday; «Туториал», только если
  читатель может пройти материал шаг за шагом и получить законченный результат;
  «Обзор» — для сравнения решений. Не выбирать формат наугад.
- **Переведённый материал:** не отмечать для собственных статей.
- **Уровень сложности:** оценивать по знаниям, нужным читателю. Для статьи с
  клиентским JavaScript, серверным кодом и базой обычно подходит «Средний».
- **Обложка:** PNG, JPG, GIF или WebP размером ровно 780×440, меньше 1 МБ.
- **Текст в ленте:** 100–2000 символов. Коротко описать проблему, затем назвать
  решение. Не пересказывать всю статью и не начинать с биографии.
- **Запланировать публикацию:** оставлять выключенным, если дата и время заранее
  не выбраны.
- **Опрос:** не добавлять, если его результат не нужен для продолжения темы.

## Готовые настройки статьи про офлайн-очередь

Статья: «Кнопка нажата, а ответа нет: как не потерять действие пользователя и
не наделать дублей».

- **Тип публикации:** Статья.
- **Язык:** Русский.
- **Целевая аудитория:** Разработка и инженерия.
- **Хабы:** Веб-разработка, JavaScript, Python, Проектирование API, PostgreSQL.
- **Ключевые слова:** офлайн-очередь, Service Worker, идемпотентность, IndexedDB,
  Background Sync, повторные запросы, FastAPI, PostgreSQL, htmx, Playwright.
- **Формат:** Кейс.
- **Переведённый материал:** нет.
- **Уровень сложности:** Средний.
- **Обложка:** `docs/habr-screenshots/s-12-offline-queue-cover-780x440.png`.
- **Текст кнопки:** `Разобраться с повторами`.
- **Запланировать публикацию:** нет.
- **Опрос:** нет.

Текст в ленте:

> Пользователь нажал кнопку, сеть пропала, а браузер не знает, дошёл ли запрос
> до сервера. Повторите запрос — можно получить дубль. Не повторяйте — потеряете
> действие.
>
> Показываю схему, которая решает обе проблемы: API без `toggle`, ключ
> идемпотентности в PostgreSQL, очередь в IndexedDB, Service Worker и проверка
> офлайна в Playwright. Это не полный offline-first — только защита действий в
> момент обрыва связи.

## Обложки и изображения

- Изображения статьи хранить в `docs/habr-screenshots/`.
- Имя нового файла: `s-NN-короткое-имя.png`.
- Публичный URL: `https://getdoday.ru/habr-img/<имя-файла>`.
- Для тела статьи можно сохранить увеличенную версию 1560×880.
- Для поля «Обложка» обязательно сделать отдельную версию 780×440 и проверить,
  что она весит меньше 1 МБ.
- Перед добавлением скриншота проверить, что на нём видна именно функция из
  текста, а не просто интерфейс Doday.

## Подготовка страницы для копирования

1. Сохранить исходник как `docs/articles/YYYY-MM-DD-habr-<slug>.md`.
2. Добавить slug и путь к исходнику в `scripts/build_marketing_html.py`.
3. Добавить slug в оба allowlist в `app/pages/router.py`.
4. Собрать HTML:

   ```powershell
   uv run python scripts/build_marketing_html.py
   ```

5. Проверить страницы:

   - `https://getdoday.ru/marketing-preview/<slug>` — предпросмотр;
   - `https://getdoday.ru/marketing-preview/<slug>/raw` — чистый Markdown.

## Проверка перед push

Форматирование обязательно: CI падает и на `ruff format --check`.

```powershell
uv run python -m ruff check .
uv run python -m ruff format --check .
uv run python -m mypy --strict scripts/build_marketing_html.py app/pages/router.py
uv run python -m pytest tests/test_seo_pages_and_invite.py -q
```

После публикации открыть статью как обычный читатель и проверить заголовок,
обложку, блоки кода, ссылки, подпись, раскрытие работы с ИИ и финальную фразу.

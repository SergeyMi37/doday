У меня планировщик для школьников. Открывают его с телефона — в школе, где вайфай держится на честном слове, или в метро по дороге домой.

Сцена, ради которой всё это затевалось: человек открывает список, жмёт на кружок «готово» — и ничего не происходит. Кружок не закрашивается, ошибки нет, вообще ничего. Он жмёт ещё раз. Потом убирает телефон в карман, а вечером видит задачу невыполненной. Или, если повезёт меньше, видит две одинаковые задачи.

Это не про экзотику вроде «полностью офлайновое приложение». Это про полсекунды без сети в момент, когда запрос уже ушёл, а ответ ещё не вернулся.

Дальше — что с этим делать: сначала на сервере, потом в браузере. И где я при этом наступил на грабли.

## Что на самом деле происходит при обрыве

Клиент отправил POST и не получил ответа. С его точки зрения это одно событие — «ошибка сети». На сервере в этот момент могло произойти три разных вещи:

1. запрос не дошёл, ничего не случилось;
2. запрос дошёл, работа сделана, но ответ потерялся по дороге обратно;
3. запрос дошёл, но упал на середине.

Различить их клиент не может. Совсем. У него есть только таймаут и пустота.

Отсюда и тупик. Не повторять — значит терять действия человека в случае (1). Повторять — значит делать работу дважды в случае (2). В списке задач это две одинаковые строки, в интернет-магазине — два заказа, в банке — два перевода.

Обычно выбирают «не повторять», потому что дубли заметнее. Пропажу человек спишет на себя: «наверное, не нажал».

## Шаг 1: сначала ручки, потом транспорт

Прежде чем городить очереди, стоит посмотреть на свои эндпоинты. У меня в коде жила вот такая:

```python
@router.post("/tasks/{task_id}/toggle")
async def toggle_task(task_id: UUID, ...):
    if task.is_completed:
        task = await uncomplete_task(session, user.id, task_id)
    else:
        task = await complete_task(session, user.id, task_id)
    return _row_response(...)
```

Удобно: кнопка одна, состояние сервер вычислит сам. Ровно до первого повтора.

Повторите `toggle` — и он отменит действие, которое только что выполнил. Человек отметил задачу, запрос ушёл дважды (нажал два раза, или это сделала за него ваша будущая очередь) — задача снова не выполнена. С точки зрения пользователя приложение просто издевается.

С повторяющимися задачами хуже. У меня при закрытии такой задачи создаётся следующий экземпляр — «тренировка в следующий понедельник». Два `toggle` подряд дают: закрыли, создали следующую, открыли обратно, потом снова закрыли и создали ещё одну. Две тренировки в календаре на ровном месте.

Лечится тем, что клиент перестаёт спрашивать «переключи» и начинает говорить, чего он хочет:

```python
@router.post("/tasks/{task_id}/state")
async def set_task_state(task_id: UUID, completed: Annotated[str, Form()], ...):
    want_done = completed.lower() in ("1", "true", "on", "yes")
    task = await get_task(session, user.id, task_id)
    if task.is_completed != want_done:
        task = await (complete_task if want_done else uncomplete_task)(
            session, user.id, task_id
        )
    return _row_response(...)
```

Разница в две строчки, а свойство появилось важное: сколько раз ни повтори — результат один и тот же. Проверка `if task.is_completed != want_done` тут не для экономии запроса к базе, а чтобы повтор не создал второй экземпляр повторяющейся задачи.

В шаблоне кнопка теперь шлёт желаемое состояние:

```html
hx-post="/htmx/tasks/{{ task.id }}/state"
hx-vals='{"completed": "{{ "false" if task.is_completed else "true" }}"}'
```

Это самая дешёвая часть всей истории, и она полезна сама по себе — даже если никакой очереди вы делать не будете. `PUT`-подобные ручки («сделай так») переживают повтор, `POST`-подобные («переключи», «добавь ещё один») — нет.

Но с созданием сущности фокус не проходит. «Добавь задачу „купить тетрадь“» — это не описание состояния, это действие. Две одинаковые задачи — совершенно законный результат, если человек правда добавил две. Здесь нужен другой механизм.

## Шаг 2: Idempotency-Key — имя для запроса

Идея простая: пусть клиент сам придумает запросу имя и повторяет его под этим же именем. Сервер выполняет работу только под первым именем, на повторы отдаёт сохранённый ответ.

Так устроены платёжные API — Stripe, YooKassa и прочие требуют `Idempotency-Key` ровно по этой причине. Цена задвоения там просто выше, чем раздражение.

Таблица под это нужна такая:

```python
class IdempotencyKey(Base):
    __tablename__ = "idempotency_keys"
    __table_args__ = (UniqueConstraint("user_id", "key", name="uq_idempotency_user_key"),)

    key: Mapped[str] = mapped_column(String(80), nullable=False)
    user_id: Mapped[UUID] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"))
    method: Mapped[str] = mapped_column(String(10))
    path: Mapped[str] = mapped_column(String(300))
    completed_at: Mapped[datetime | None]
    status_code: Mapped[int | None]
    body: Mapped[str | None]
    created_at: Mapped[datetime]
```

Три вещи, ради которых стоило это писать.

**Строка создаётся до выполнения работы и служит замком.** Не после — до. Уникальный индекс `(user_id, key)` решает, кто из одновременно прилетевших запросов делает работу, а кто ждёт:

```python
inserted = await session.execute(
    pg_insert(IdempotencyKey)
    .values(key=key, user_id=user_id, method=request.method, path=path)
    .on_conflict_do_nothing(index_elements=["user_id", "key"])
    .returning(IdempotencyKey.id)
)
row_id = inserted.scalar_one_or_none()
await session.commit()
```

Если `row_id` пустой — строку создал кто-то другой. Дальше два случая: работа уже закончена (`completed_at` заполнен) — отдаём сохранённый ответ; работа ещё идёт — отвечаем `409` и заголовком `Retry-After`. Просить клиента зайти попозже честнее, чем выполнять вторую копию той же работы.

Обратите внимание: замок — это строка в таблице, а не блокировка. Транзакция коммитится сразу, до вызова обработчика, поэтому никакие локи во время долгой работы не висят.

**Ключ принадлежит пользователю.** Пара `(user_id, key)`, а не просто `key`. Иначе я подберу чужой ключ и получу чужой ответ — там HTML с чужими задачами.

**После 5xx ключ надо отпустить.** Это неочевидная часть. Если обработчик упал с 500, работа, скорее всего, не сделана — и повтор должен быть настоящим повтором, а не «уже выполнено, вот вам пустота»:

```python
if response.status_code >= 500:
    # Сервер упал — работа, скорее всего, не сделана. Ключ убираем,
    # чтобы повтор был настоящим повтором, а не «уже выполнено».
    await session.delete(row)
```

«Скорее всего» здесь честное слово. Строго говоря, 500 мог случиться после того, как задача создалась. Стопроцентной гарантии без распределённых транзакций не бывает; выбор между «иногда дубль после падения сервера» и «иногда молча потерянное действие» я сделал в пользу первого.

Ещё один случай: тот же ключ пришёл на другую ручку. Это не повтор, это ошибка клиента — отвечаю `422`, чтобы она не превратилась в загадочный баг через полгода.

Живут ключи сутки. Клиент повторяет неотправленное минуты, в плохом случае — часы; через сутки ключ уже никому не нужен, а таблица растёт с каждым действием в приложении. Уборка — одна строка в том же месте, где чистится остальное:

```sql
DELETE FROM idempotency_keys WHERE created_at < now() - interval '1 day'
```

### Грабли: middleware, который не видит сессию

Реализовать это зависимостью FastAPI не получится: зависимость видит запрос до обработчика и не может подменить результат. А нам нужен готовый ответ, чтобы сохранить его для повторов. Значит, middleware.

И вот тут я потерял полчаса. Регистрируешь middleware как обычно — и `request.session` внутри падает с `AssertionError`.

Дело в порядке. Starlette вставляет каждый следующий middleware **снаружи** предыдущего: добавленный позже оборачивает добавленных раньше. `SessionMiddleware` в моём `main.py` стоял первым, значит все мои `@app.middleware("http")` оказались снаружи — и работали до того, как сессия вообще появилась в запросе.

Проверяется за минуту:

```python
app.add_middleware(SessionMiddleware, secret_key="x")

@app.middleware("http")
async def mw(request, call_next):
    request.session   # AssertionError: SessionMiddleware must be installed
    return await call_next(request)
```

Лечится переносом регистрации на строку выше `SessionMiddleware`. Я оставил в коде комментарий, потому что через месяц кто-нибудь (я) переставит строки местами и будет искать причину заново.

## Шаг 3: очередь в браузере

Теперь сервер готов принимать повторы. Осталось, чтобы кто-то их делал.

Этим занимается service worker: он видит все запросы страницы и может ответить на них сам. Логика на словах — «попробуй отправить, а если сеть отказала, положи в коробку и скажи странице, что мы запомнили»:

```js
e.respondWith(
  fetch(req).catch(async () => {
    const body = await copy.text();
    await enqueue({ url: req.url, method: req.method, headers, body, at: Date.now() });
    await tellPages({ type: 'outbox', pending: (await allQueued()).length });
    if ('sync' in self.registration) {
      try { await self.registration.sync.register(SYNC_TAG); } catch (err) {}
    }
    return new Response('', {
      status: 202,
      headers: { 'X-Doday-Queued': '1', 'HX-Reswap': 'none' },
    });
  })
);
```

Несколько мест, где легко ошибиться.

**Тело запроса читается один раз.** `req.clone()` надо сделать до того, как запрос ушёл в `fetch`, иначе в обработчике ошибки читать будет уже нечего.

**Хранить очередь надо в IndexedDB.** Не потому что она лучше, а потому что `localStorage` синхронный и в service worker недоступен в принципе.

**Порядок имеет значение.** Если сеть отвалилась посреди отправки очереди — останавливаемся и ждём следующего раза, а не пытаемся отправить остальное:

```js
} catch (e) {
  // Сеть снова пропала. Остальное ждёт следующего раза — порядок
  // важен: «создать задачу» должно уйти раньше «отметить её».
  break;
}
```

То же самое при `409` (первый такой же запрос ещё выполняется) и при `5xx`. А вот `4xx` — это окончательный отказ: задачу, например, успели удалить с другого устройства. Такой запрос из очереди убираем, повторять его бессмысленно.

**Background Sync есть не везде.** Браузер умеет сам разбудить воркер, когда сеть вернётся, — но в Safari этого API нет до сих пор. Поэтому страница дополнительно слушает событие `online` и толкает воркер сама:

```js
window.addEventListener('online', function () {
  navigator.serviceWorker.ready.then(function (r) {
    r.active && r.active.postMessage({ type: 'flush' });
  });
});
```

**Человеку надо сказать, что происходит.** Молчаливая очередь ничем не лучше молчаливой потери: пользователь всё равно не знает, сохранилось или нет. У меня это полоска внизу экрана — «Одно изменение ждёт сети», — которая исчезает, когда очередь ушла.

### Грабли: htmx и ответ, которого он не ждал

У меня интерфейс на htmx: кнопка шлёт POST и подставляет пришедший HTML на место строки задачи. Ответ «положили в очередь» никакого HTML не содержит — и первая же версия честно стёрла строку задачи с экрана. Человек нажал «готово», и задача исчезла вообще.

Спасает заголовок `HX-Reswap: none` — им сервер (в нашем случае воркер) говорит htmx: ответ получен, подставлять ничего не надо. Строка остаётся на месте, а страница помечает её как неотправленную.

### Грабли: воркер, который сломал мне CDN

Самое обидное я нашёл тестом. Первая версия обработчика `fetch` перехватывала **все** GET-запросы, включая `unpkg.com` и `cdn.tailwindcss.com`. Логика была «сходи в сеть, не вышло — отдай из кеша, не вышло — отдай 503».

Работает, пока CDN отвечает. А прогонял я тест в окружении, где внешние адреса недоступны, — и случилось вот что: htmx не загрузился, потому что мой же воркер вернул на него `503`. Кнопки перестали быть кнопками. При этом собственный сайт открывался нормально — и со стороны это выглядело как «htmx сломался».

Мораль простая: чужие домены не ваше дело.

```js
if (url.origin !== self.location.origin) return;
```

Одна строка, а без неё любой сбой у стороннего CDN превращается в отказ вашего приложения — причём в такой, который вы будете искать в своём коде.

## Как это проверять

Тесты на сервер очевидны — берём один и тот же ключ и смотрим, сколько задач получилось:

```python
async def test_repeat_with_same_key_creates_one_task(logged_in_client, db_session):
    payload = {"text": "Купить тетрадь"}
    headers = {"Idempotency-Key": "key-abc-123"}

    first = await logged_in_client.post("/htmx/quickadd", data=payload, headers=headers)
    second = await logged_in_client.post("/htmx/quickadd", data=payload, headers=headers)

    assert second.text == first.text                      # ответ тот же, а не новый
    assert second.headers.get("Idempotency-Replayed") == "1"
    assert await _task_count(db_session, "Купить тетрадь") == 1
```

А вот очередь тестом на сервере не проверишь никак: она целиком живёт в браузере. Playwright умеет выключать сеть у контекста, и это ровно то, что нужно:

```js
await ctx.setOffline(true);
await circle.click();                       // жмём «готово» без сети
// значок появился, запрос лёг в IndexedDB
await ctx.setOffline(false);
await page.evaluate(() => window.dispatchEvent(new Event('online')));
```

Вывод такого прогона выглядит так:

```
воркер управляет страницей: true
— сеть выключена —
  [ответ] 202 /htmx/tasks/47583447-.../state
значок очереди виден: true | Одно изменение ждёт сети
в очереди: ["POST /htmx/tasks/47583447-.../state"]
— сеть включена —
осталось в очереди: 0
```

И финальная проверка — в базе, а не на экране:

```
        title         | is_completed
----------------------+--------------
 Физика: задачи 12–15 | t
```

Именно этот тест и нашёл историю с CDN. Пока я кликал руками в обычном браузере, всё работало.

## Когда всё это не нужно

Не надо делать очередь, если действия пользователя — только чтение. Список, который не открылся, человек просто откроет ещё раз; хранить нечего.

Не надо повторять то, что имеет смысл только сейчас. Вход, оплата, отправка кода из СМС — запрос, который доехал через сорок минут, скорее навредит. У меня такие пути прямо исключены из очереди:

```js
return !/^\/(auth|api\/billing|miniapp\/auth)/.test(url.pathname);
```

И это не полноценная офлайн-синхронизация. Тут нет разрешения конфликтов: если задачу поменяли на двух устройствах, победит тот, чей запрос дошёл позже. Для планировщика этого достаточно — а если вам нужно больше, вы уже смотрите в сторону CRDT, и это разговор другого масштаба и другой цены.

Порядок, в котором я бы это делал заново:

1. Убрать из API ручки вида «переключи». Бесплатно, полезно сразу, ничего не ломает.
2. Добавить `Idempotency-Key` там, где создаются сущности. День работы, зато повторы становятся безопасными — и не только из очереди, но и от двойного клика.
3. И только потом — очередь в браузере. Без первых двух пунктов она превращается в машину по производству дублей.
